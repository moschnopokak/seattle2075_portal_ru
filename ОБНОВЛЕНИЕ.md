# Обновление портала на сервере (с защитой базы данных)

Для работающего портала, который стоит по инструкции из `ЗАПУСК.md` (Docker, папка `/opt/seattle2075-portal`). Обновление делает один скрипт, `deploy/update.sh`. Он ничего не заменяет, пока не убедится, что база переживёт обновление, а если что-то идёт не так, сам возвращает всё как было.

## Как защищена база

1. **Репетиция на копии.** Скрипт копирует базу средствами SQLite (портал при этом работает), прогоняет на копии настоящий запуск новой версии и проверяет: миграция схемы проходит, база цела, ни одна строка не пропала и не изменилась, мастер и каждый игрок получают свои данные, дневник каждого персонажа собирается, все картинки и раздатки на месте. Ваша настоящая база в репетиции не участвует.
2. **Полная копия перед заменой.** Портал останавливается на пару минут, и вся папка `data` (база, ключ входа, копии) копируется в `/opt/portal-backups/<время>/`. Это вне папки портала: никакая команда внутри `/opt/seattle2075-portal` до неё не доберётся. Туда же уходят старый код, настройки и метка старого образа.
3. **Сверка после запуска.** Когда новая версия запустилась, скрипт сравнивает базу с копией «до» построчно: ничего из прежнего не должно пропасть.
4. **Автоматический откат.** Не запустилось, не стало здоровым, из базы что-то пропало: скрипт сам возвращает старый код и базу из копии. То, что новая версия успела записать, не выбрасывается, а лежит рядом в `data.after-update-<время>`.
5. **Миграции только добавляют.** Новые таблицы и столбцы появляются, старые не трогаются и не удаляются. Поэтому игроки остаются залогиненными: ключ входа `data/secret.key` не меняется.

На базе, которую вы прислали (схема первой версии, 14 записей, 367 элементов, 38 сообщений, 50 картинок), репетиция прошла без замечаний. Кроме того, я прогнал на этой базе настоящий код первой версии и новый: мастер и все четыре игрока видят в обеих версиях одно и то же, добавились только новые разделы.

## Что понадобится

- доступ к серверу по SSH и `sudo`;
- свободное место: втрое больше папки `data` и ещё около 600 МБ (скрипт проверит сам);
- 10–15 минут, из которых портал недоступен 2–5. Лучше не в день игры. Игрокам достаточно написать «портал недоступен несколько минут».

## Шаг 1. Скачать новую версию рядом, не поверх

Папку `/opt/seattle2075-portal` не трогаем: новую версию кладём рядом.

```bash
sudo rm -rf /opt/portal-new && sudo mkdir -p /opt/portal-new
curl -fL https://github.com/moschnopokak/seattle2075_portal_ru/archive/refs/heads/main.tar.gz | sudo tar -xz -C /opt/portal-new --strip-components=1
ls /opt/portal-new/deploy
```

В списке должны быть `update.sh`, `rollback.sh`, `filehash.py`, `known-files.txt`.

Если репозиторий приватный и `curl` отвечает ошибкой: на своём компьютере откройте репозиторий на GitHub, нажмите «Code», «Download ZIP» и загрузите архив на сервер (WinSCP или `scp`). Затем на сервере (нужен `unzip`: `sudo apt install -y unzip`):

```bash
sudo rm -rf /opt/portal-new /tmp/p && sudo mkdir -p /opt/portal-new /tmp/p
sudo unzip -q ~/архив.zip -d /tmp/p && sudo cp -a /tmp/p/*/. /opt/portal-new/ && sudo rm -rf /tmp/p
```

## Шаг 2. Копия базы к себе на компьютер (по желанию, но лучше сделать)

Скрипт сделает копию на сервере, но копия на другом компьютере надёжнее. На сервере:

```bash
sudo python3 -c "import sqlite3; s=sqlite3.connect('/opt/seattle2075-portal/data/portal.db'); d=sqlite3.connect('/tmp/portal-before-update.db'); s.backup(d); d.close()"
sudo chown "$USER" /tmp/portal-before-update.db
```

На своём компьютере: `scp ВАШ_ЛОГИН@АДРЕС_СЕРВЕРА:/tmp/portal-before-update.db .` (или скачайте файл через WinSCP). Потом на сервере `rm /tmp/portal-before-update.db`.

## Шаг 3. Репетиция (ничего не меняет)

```bash
cd /opt/portal-new
sudo bash deploy/update.sh --rehearse-only
```

Первый запуск собирает образ новой версии, это несколько минут. Портал всё время работает. В конце должна быть строка `Итог: можно обновлять.` и такие галочки:

```
  ✓ Целостность базы: ok
  ✓ Миграция прошла: схема 0 → 10
  ✓ Целостность после миграции: ok
  ✓ Все данные на месте: 484 строк в 7 таблицах не потеряно и не изменено
  ✓ Мастер и игроки (5) получают своё состояние, дневников собрано 6, записей 14
  ✓ Картинки и раздатки, на которые ссылаются карточки, на месте
Итог: можно обновлять.
```

(числа будут вашими). Если есть красные `✗`, на этом всё: ничего не изменено, пришлите вывод тому, кто сопровождает портал.

Ещё скрипт сообщит, если в `app/` или `static/` лежат файлы, которых нет ни в одной известной версии портала (вы правили их вручную). Правила простые:

- файл, который есть и в новой версии, будет заменён её вариантом (ваш вариант останется в `code-before.tgz` внутри папки копии);
- файл, которого в новой версии нет, останется на месте, скрипт его не тронет и в конце напишет об этом.

Если вы правили что-то, чего я ещё не видел, пришлите мне до обновления: правки нужно перенести в новую версию, иначе они пропадут из рабочей папки.

## Шаг 4. Обновление

```bash
cd /opt/portal-new
sudo bash deploy/update.sh
```

Скрипт повторит репетицию, спросит «Обновлять сейчас?» (ответ `y`), остановит портал, сделает полную копию, заменит код, запустит новую версию, дождётся, пока она станет здоровой, и сверит базу. В конце напишет `Готово: портал обновлён`, где лежит копия и как откатиться.

Не пугайтесь, если связь с сервером оборвётся: скрипт игнорирует разрыв SSH и дойдёт до конца сам. Через пять минут зайдите снова и проверьте: `cd /opt/seattle2075-portal && sudo docker compose ps` (у `app` должно быть `healthy`). Сомневаетесь, откатывайтесь (ниже).

Что остаётся нетронутым: `.env`, `config/players.toml`, `config/campaign.json`, вся папка `data`, тома Caddy с сертификатом.

## Шаг 5. Проверить

1. `cd /opt/seattle2075-portal && sudo docker compose ps`: у `app` статус `healthy`, у `caddy` `Up`.
2. Откройте `https://ваш-домен/healthz`: в ответе `"ok": true`.
3. Войдите мастером: календарь, записи, досье с картинками, раздатки на месте. Нажмите «Посмотреть глазами игрока».
4. Попросите одного игрока открыть портал: он должен быть уже залогинен.
5. `sudo docker compose logs --tail 50 app`: без строк с `ERROR`.
6. Новое: «Мой дневник» (выгрузка в Markdown и PDF), броски кубов в обсуждении, листы персонажей, линейка на карте, корзина и история изменений.

## Если что-то не так: откат

```bash
ls -1 /opt/portal-backups
sudo bash /opt/portal-backups/<время-самой-свежей-папки>/rollback.sh
```

Скрипт остановит портал, вернёт базу и код из копии «до» и запустит старую версию. Всё, что игроки записали после обновления, из рабочей базы пропадёт, но не уничтожится: оно лежит в `/opt/seattle2075-portal/data.after-update-<время>`.

Откатывайте только этим скриптом, не подменяйте вручную одну папку `app`: новая версия может положить в базу файлы форматов (PDF, картинки, аудио в раздатках), которые старая не откроет. Скрипт возвращает код и базу вместе.

## Ваша доработка карты уже перенесена

На вашем сервере была добавлена функция «Импорт мест»: набор точек из «Seattle 2072», загрузка KML из Google My Maps, фоновые места с переключателем «Фон» на карте и новые типы мест (медицина, полиция и тюрьмы, магазины, еда и отдых). Я перенёс её в новую версию целиком, вместе с файлами `static/map/poi_seattle2072.json`, `llgrid.json` и лицензией `POI_LICENSE.txt` (набор распространяется по MIT, лицензия лежит рядом). Вы увидите то же, что было: кнопку «Импорт мест» у мастера и переключатель «Фон» у всех. Добавилось:

- единственная запись в журнале изменений на весь импорт («Импорт мест: N»), а не сотни отдельных строк; отменить импорт можно удалением мест (они уходят в корзину);
- общий предел в 1500 мест на карте и в 600 за один импорт;
- проверки на сервере: чужие точки проходят ту же проверку, что и ручные, и при любой ошибке не добавляется ни одна;
- вид переключателя «Фон» запоминается в браузере.

Варианты ваших файлов `app/logic.py`, `app/main.py` и `static/index.html` занесены в список известных (`deploy/known-extra.txt`), поэтому скрипт не будет считать их чужими правками.

## Что изменилось на сервере

- **`docker-compose.yml`:** остальная файловая система контейнера портала теперь только для чтения (пишется лишь `data`, я проверил запись по всем сценариям: раздатки, картинки, дневники, копии, корзина), лишние права отобраны, журналы ограничены (10 МБ × 3), Caddy стартует после того, как портал здоров.
- **`deploy/Caddyfile`:** заголовок `Strict-Transport-Security` на год (браузеры будут ходить на портал только по https: у вас он и так есть), лимит тела запроса 16 МБ под раздатки, скрыт заголовок `Server`.
- **`.env`:** не меняется. Новые настройки необязательны, у всех безопасные значения по умолчанию, в конце обновления скрипт перечислит те, которых нет в вашем `.env` (описания в `.env.example`). Стоит добавить `DEFAULT_TZ=Europe/Moscow`: по нему считаются тихие часы и сводка, по умолчанию стоит UTC. `ANTHROPIC_API_KEY` пуст: пересказ «Что было раньше» выключен и никуда ничего не отправляется. `CSP_MODE=report-only`: защитная политика страницы только пишет в журнал и ничего не блокирует.
- **Пересказ через мастера:** необязательно. Если добавить в `.env` строку `RECAP_MODE=gm` и перезапустить портал, игроки смогут просить пересказ «Что было раньше», а вы будете готовить его в своём обычном чате с Claude (без ключа API и без оплаты); как это работает, описано в `ЗАПУСК.md`. База при обновлении получает одну новую таблицу для таких просьб (схема 7 → 8), старые данные не меняются.
- **Что видят игроки вперёд:** в панели мастера новый раздел с переключателем. По умолчанию выключен, поэтому после обновления игроки видят то же, что и раньше. Чтобы они не заглядывали дальше текущей арки, нажмите «До конца текущего этапа»; описание в `ЗАПУСК.md`. База не меняется.
- **Загрузка разбора арки:** в панели мастера новый раздел «Загрузить разбор арки», а в проекте файл `ПРОМПТ_РАЗБОР_АРОК.md` для чатов, где вы разбираете арки. База для этого не меняется (новых таблиц нет), включать ничего не нужно; как это работает, описано в `ЗАПУСК.md`.
- **Карты места:** новый раздел «Локации» (рисунок игроков и карта мастера, метки, лента «Что изменилось», пометки группы) и файл `ПРОМПТ_КАРТА_ЛОКАЦИИ.md` для чата, где вы делаете план места. У меток могут быть контуры зон, и мастер может разрешить игрокам отмечать их («расчищено», «опасно»). Для игры: сроки по игровым датам, «Мы здесь», вопросы мастеру, счётчик мастера с правилами расчистки, журнал с отменой, связи с досье, картинка карты, значок «новое». В базе появляются новые таблицы и колонки (схема 8 → 10), старые данные не меняются; пока вы не добавите карту, игроки раздела не видят. Как это работает, описано в `ЗАПУСК.md`.
- **Уведомления:** теперь у портала есть очередь и планировщик. Сообщения обсуждения склеиваются («N новых сообщений» через 5 минут), у каждого игрока есть тихие часы и сводка в «Уведомлениях», о приглашениях без ответа напоминают через 2 дня (не больше двух раз). Приглашения, которые к моменту обновления уже висят без ответа, отсчитывают эти 2 дня от момента обновления, а не от своей даты. Предупредите игроков.

## Через две недели: уборка

Если всё хорошо и никто не жалуется:

```bash
sudo rm -rf /opt/portal-new
sudo rm -rf /opt/seattle2075-portal/data.after-update-*      # только если откатывались
sudo rm -rf /opt/portal-backups/<старые папки>               # копии «до обновления» храните не меньше двух недель
sudo docker image rm seattle2075-portal-before-update:<метка> seattle2075-portal-rehearsal
```

Регулярные копии базы на каждый день и отправку их в Telegram настраивает раздел 13 в `ЗАПУСК.md`. Проверьте, что они идут: `ls -la /opt/seattle2075-portal/data/backups`.

## Если скрипт остановился с ошибкой

| Что видно | Что значит и что делать |
|---|---|
| `Запускайте через sudo` | Запустите команду с `sudo`. |
| `В … нет .env` или другого файла | Скрипт ищет портал в `/opt/seattle2075-portal`. Если он лежит в другом месте: `--install-dir ПАПКА`. |
| `Мало места на диске` | Освободите место: `sudo docker system prune -a` (удалит неиспользуемые образы), старые копии в `data/backups`. |
| `Репетиция нашла проблемы` | Портал и данные не тронуты. Пришлите вывод скрипта. |
| `Сбой на строке …`, затем `Портал не останавливался` | Ничего не менялось, ваши данные нетронуты. |
| `Откатываюсь к состоянию до обновления…` | Откат идёт автоматически; дождитесь строки `Откат выполнен`. Старая версия работает, данные из копии. |
| `Автоматический откат не удался` | Данные в безопасности (`/opt/portal-backups/<время>/data`). Выполните вручную `sudo bash /opt/portal-backups/<время>/rollback.sh` и пришлите вывод. |

## Для сопровождающего: как устроено

- `app/preflight.py`: репетиция (`python -m app.preflight --db ФАЙЛ`) и построчная сверка двух баз (`--compare СТАРАЯ НОВАЯ`).
- `deploy/update.sh`, `deploy/rollback.sh`: обновление и откат. Копия `rollback.sh` кладётся в папку каждой резервной копии вместе с `install-dir`, `data/`, `code-before.tgz`, `portal-before.db`, `portal-after.db`.
- `deploy/filehash.py`, `deploy/known-files.txt`, `deploy/known-extra.txt`: поиск ручных правок в `app/` и `static/`. Список известных версий пересобирается перед выпуском: `python deploy/filehash.py --from-git > deploy/known-files.txt`; `known-extra.txt` ведётся вручную (варианты файлов с серверов, правки из которых уже перенесены в код). После первого обновления сервер сравнивает уже с `.installed-files.sha256` (отпечатки только файлов новой версии), который записал сам скрипт; добавленные вами файлы, которых нет в релизе, при каждом обновлении остаются на месте.
- Тесты: `tests/test_legacy_upgrade.py` (база, созданная настоящим кодом первой версии, `tests/fixtures/legacy_v1.*`) и `tests/test_update_scripts.py` (сценарии скриптов на заглушке docker `tests/tools/fake_docker.sh`: успех, отмена, провал репетиции, зависший запуск, потеря данных после запуска, обрыв во время копирования, ручной откат, WAL с незаписанными данными).
- Для тестов скрипты понимают переменные `DOCKER`, `PYTHON`, `CURL`, `CHOWN`, `PUBLIC_CHECK_PAUSE`, `ASSUME_ROOT`. На сервере их задавать не нужно.
